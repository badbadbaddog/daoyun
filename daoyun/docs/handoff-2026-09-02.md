## 4. 推荐排序后端：已解决“推荐退化成最新”核心问题

### 4.1 根因

原 `FeedMode::Recommended` 使用 Popular 排序，但 `topics.hot_score` 在生产路径没有随真实互动更新，绝大多数主题实际为 `hot_score = 0`，导致推荐在置顶之后几乎退化成按发布时间排序。

### 4.2 当前实现

新增迁移：

- `migrations/202609020001_derive_topic_hot_score_from_engagement.up.sql`
- `migrations/202609020001_derive_topic_hot_score_from_engagement.down.sql`
- `migrations/202609020002_add_global_recommended_topic_index.up.sql`
- `migrations/202609020002_add_global_recommended_topic_index.down.sql`
- `migrations/202609020003_saturate_topic_hot_score_on_large_counts.up.sql`
- `migrations/202609020003_saturate_topic_hot_score_on_large_counts.down.sql`

当前确定性评分：

```text
hot_score = 8 * like_count + 12 * reply_count
```

说明：

- 不使用 `view_count`，因为当前浏览量没有可靠生产写路径。
- `202609020001` 使用 PostgreSQL trigger 在 INSERT / like_count / reply_count 更新时重新计算 hot_score。
- 迁移已经包含现有主题的 backfill：`UPDATE topics SET hot_score = ...`。
- `202609020002` 增加全局推荐索引：`(hot_score DESC, published_at DESC, id DESC)`，仅覆盖 published 且未删除主题。
- 最终 `cargo test --workspace` 发现极端 `like_count` / `reply_count` 会让 PostgreSQL trigger 的 bigint 中间乘法先溢出；`202609020003` 改用 `numeric` 做中间计算，并把 `hot_score` 安全饱和到 `i64::MAX`，避免评分派生字段反过来破坏合法计数更新。
- 饱和只作用于派生 `hot_score`；真实 `like_count` / `reply_count` 本身的 bigint 溢出仍会失败并保持事务回滚语义。
