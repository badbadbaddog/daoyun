# ADR-008：核心最小化与后续业务插件优先

## 状态

Accepted

## 日期

2026-08-15

## 背景

DaoYun已经具备账号状态、RBAC/ABAC、积分与会员账本、审计、Outbox以及基于Wasmtime Component Model的插件沙箱。后续还需要VIP、签到、任务、勋章认证、悬赏、付费内容、红包、抽奖、投票和支付渠道等大量可选功能。

如果持续把这些功能直接加入核心，核心数据库、权限矩阵、后台导航和发布节奏会不断膨胀；不同自托管实例也无法只启用自己需要的能力。如果把账号授权、账本或审计整体下放给插件，又会允许可停用组件影响全站安全和事实来源。

当前 `daoyun:plugin@0.1.0` world没有host import，只支持 `content-transform` 和静态 `ui-render`。它适合纯转换和只读面板，不足以承载完整业务插件。

## 决策

采用“核心提供可信底座，官方与第三方插件提供可选业务”的边界：

1. 账号、会话、账号状态、用户组、治理角色、capability、板块作用域和最终权限判定留在核心。
2. 积分、EXP、声望账本，标准权益投影，审计、Outbox、后台任务和通知可靠投递留在核心。
3. Wasmtime执行、资源限制、能力审批、安装生命周期、数据隔离和插件调用审计留在核心。
4. VIP、活动、任务、排行榜、勋章认证、内容玩法、运营报表和外部渠道默认优先作为官方插件交付。
5. 官方插件与第三方插件使用相同的沙箱、capability、配额和审计边界，不获得数据库直连或隐式权限。
6. 不破坏 `daoyun:plugin@0.1.0` 的既有行为；业务扩展使用新的WIT package和manifest schema版本。
7. 插件只通过版本化事件、只读公共DTO、受控写命令、受限UI Schema、固定交互动作和后台任务协议与核心协作；核心请求链不为权限判定同步调用插件。
8. 插件不能自行挂载任意Axum路由、直接访问数据库、注册治理capability或执行未经批准的卸载脚本。
9. 首期继续由管理员显式安装、默认停用并手动批准能力；插件优先不要求同步建设公共市场。

每个新增host import都必须同时定义：

- 独立capability和批准流程。
- 输入输出Schema、数据最小化和稳定错误。
- CPU、内存、输入输出、调用频率、并发和存储配额。
- 审计事件、request ID、幂等语义和失败恢复。
- API/OpenAPI契约、单元测试、集成测试和真实浏览器测试。

## 核心准入条件

新功能只有满足以下任一条件时才进入核心：

- 属于账号、安全、授权、账本、审计、Outbox或插件沙箱等可信计算基座。
- 必须与核心事务原子提交，异步事件和补偿仍不能满足一致性。
- 是多个插件共同依赖的稳定公共能力，放入单一插件会形成循环依赖或事实垄断。
- 涉及全站最终拒绝、最后管理员保护或不可委托的安全策略。

其他功能默认先按插件方案设计，并说明需要的事件、查询、命令、UI插槽、后台任务和数据配额。

## 运营交互

插件详情必须让管理员看清来源、版本、SHA-256、签名状态、能力清单、数据范围、事件订阅、UI插槽、后台任务、配额、健康状态和私有数据去向。

安装与升级采用：

```text
检查来源与签名
→ 展示新增/移除能力和数据范围
→ 展示数据迁移与回滚限制
→ 管理员明确批准
→ 默认停用安装或受控升级
→ 健康检查
→ 启用
→ 持续审计和监控
```

停用插件后，入口立即隐藏、事件和任务停止领取、新调用被拒绝；历史数据、审计和用户记录按保留策略继续可查。卸载前由管理员选择保留、导出或删除插件数据。

插件已经通过受控命令写入的标准权益投影不会因停用被隐式撤销。核心继续按投影中的有效期和状态判定，直到自然到期或管理员执行显式撤销，从而避免停用插件导致已售权益突然失效。

## 备选方案

### 所有功能继续加入核心

- 优点：事务和类型集成直接，实现初期简单。
- 缺点：核心持续膨胀，自托管实例无法按需组合，运营功能发布必须跟随主版本。
- 结论：拒绝；不适合长期扩展。

### 把会员与权限整体插件化

- 优点：核心表面更小。
- 缺点：可停用插件将控制全站授权、账本和审计事实来源，故障或卸载会破坏基础行为。
- 结论：拒绝；安全边界错误。

### 允许插件直接访问数据库或注册任意HTTP路由

- 优点：插件开发自由、迁移现成应用方便。
- 缺点：无法可靠执行数据隔离、最小权限、OpenAPI一致性、资源配额和卸载恢复。
- 结论：拒绝；所有访问必须经过宿主契约。

## 后果

- 正面：核心规模和安全边界稳定，运营玩法可以独立安装、启停和升级。
- 正面：官方插件可作为第三方插件的参考实现，避免官方能力依赖私有后门。
- 正面：插件故障和超时不阻塞注册、发帖、支付和治理主事务。
- 代价：必须先建设事件、受控命令、专属存储、交互UI和任务调度等宿主能力。
- 代价：跨插件工作流需要明确幂等、最终一致性和补偿语义。
- 代价：动态插件动作需要统一契约注册和OpenAPI表达，不能依赖任意自定义路由。

## 复审条件

- 受限UI Schema无法满足经过验证的核心运营场景。
- 业务插件需要同步低延迟决策，异步事件无法满足且核心受控命令不足。
- 插件数据量、任务吞吐或冷启动超过宿主配额与运营预算。
- 引入公共插件市场、自动更新、远程依赖或新的高隔离执行器。
