# ADR-007：统一站点管理入口与任务型后台

## 状态

已接受

## 日期

2026-08-12

## 背景

当前后台按照系统能力拆为 `/#admin`“系统后台”和 `/#management`“管理工作台”。这种拆分有利于代码和权限隔离，但要求站长先理解“系统配置”和“社区治理”的内部边界，才能找到用户、版块和举报相关操作。

现有实现还存在三个流程缺口：

- “用户管理”实际上只有角色与权限分配，没有用户搜索、管理员详情、账号限制和管理记录。
- 版块管理是平面列表，缺少大型社区常用的层级定位和行内调整。
- 举报处理缺少详情上下文、筛选与分页入口，内容处置、用户处置和举报状态之间的关系不够直观。

phpwind 9 证明了“搜索用户后管理”“树形管理版块”“用待办队列处理举报”三种流程对站长是有效的，但它的 iframe、多页面标签、长表单和技术化输入不适合 DaoYun 的响应式、内容优先界面。

## 决策

采用一个面向站长的 `/#admin`“站点管理”入口。前端按任务组织导航，服务端继续按 capability 做最终授权：

- 工作台：汇总待处理举报、受限用户和需要关注的版块。
- 用户管理：搜索、详情、账号限制、角色与权限、管理记录。
- 举报处理：队列、内容上下文、内容与用户的一体化处置。
- 版块管理：树形层级、行内低风险操作和带影响预览的高风险操作。
- 系统设置：品牌、会员、授权、运维和插件等低频模块。

客户端只隐藏不可用模块，不以客户端状态代替服务端授权。每个业务页面使用可分享、可刷新的 hash 子路由，例如 `/#admin/users`、`/#admin/reports?status=open`。

本决策被接受并实现后，将取代 `docs/specs/system-admin-and-management-workspace.md` 中关于两个入口、两套页面结构和客户端数据隔离的决策；细分 capability、Cookie 会话、CSRF、审计和服务端授权边界保持不变。

## 考虑过的替代方案

### 保留两个入口，只优化文案

- 优点：实现成本最低，不改变现有页面边界。
- 缺点：站长仍需判断操作属于“系统”还是“治理”，无法解决流程分散。
- 结论：拒绝。它缓解名称问题，但不解决任务发现问题。

### 完整复制 phpwind 9 的后台框架

- 优点：信息密度高，熟练管理员可同时保留多个工作页面。
- 缺点：iframe 和顶部多页面标签增加状态、可访问性和移动端适配成本；长表单与通用成功提示不符合 DaoYun 的产品边界。
- 结论：拒绝。只借鉴任务流程，不复制界面结构、源码、品牌或产品文字。

### 统一入口，并以任务组织页面

- 优点：站长只需判断“我要管理谁或什么”，无需理解系统模块边界；现有 capability 仍可复用。
- 缺点：需要调整现有路由、导航与测试，并新增用户管理、版块层级和举报详情契约。
- 结论：采用。

## 后果

- `/#management` 不再作为独立产品入口；相关治理页面迁入 `/#admin`。
- 后台导航与数据加载仍按 capability 裁剪，拥有部分权限的账号只看到可用任务。
- 需要新增用户管理 API，并扩展版块、举报和审计契约。
- 需要为危险操作提供影响预览、明确确认和可追溯结果。
- 桌面端可以使用紧凑双栏或树形布局，移动端必须折叠为单栏且不得横向溢出。
- 不引入 phpwind 兼容层，也不保留两套后台 UI。
