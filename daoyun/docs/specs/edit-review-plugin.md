# 编辑审核插件规格

## 交付目标

编辑审核是独立官方插件。插件启用后，管理员可按版块分别配置主题编辑与回复编辑是否需要审核，并在统一队列中批准或驳回待审版本。

## 已确认业务规则

- 插件能力键为 `topic.edit_review`，不复用 `topic.supplements`。
- 每个版块有两个独立开关：主题编辑需要审核、回复编辑需要审核；默认都关闭。
- 插件未安装、停用或相应版块开关关闭时，编辑沿用原有立即发布流程。
- 需要审核时，提交内容只写入独立待审记录；当前公开版本及公开修订号保持不变。
- 同一帖子同一时间只允许一个待审编辑；再次提交返回冲突。
- 批准时再次校验提交所基于的公开修订号；一致时原子地替换公开版本并追加公开修订历史。
- 驳回只结束待审记录，不改变公开内容。
- 主题编辑快照必须包含标题、摘要、正文、富文本和标签；回复编辑快照包含正文和富文本。
- 审核配置支持一次选择多个版块并原子保存，不使用单选版块逐个提交。

## 权限与插件边界

- 宿主按已安装且已启用的 `topic.edit_review` provider 判定功能是否生效，不按官方插件 key 写死。
- 配置读取/写入沿用 `admin.configuration.read/write`，并按版块作用域校验。
- 审核读取和处理沿用版块作用域的 `moderation.topic`；插件自身不能直连数据库。
- 编辑审核状态不复用主题整体治理的 `moderation_status`，也不写入公开 `post_revisions`。

## 数据模型

- `edit_review_policies`：`board_id`、`review_topic_edits`、`review_reply_edits`、更新时间。
- `content_edit_reviews`：目标帖子、目标类型、提交人、基础公开修订号、完整候选快照、状态、审核人、原因和时间。
- `content_edit_reviews` 对 `status = 'pending'` 的 `post_id` 建唯一部分索引。

## 接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET / PUT | `/api/v1/admin/edit-review/policies` | 读取可配置版块 / 批量保存版块策略 |
| GET | `/api/v1/admin/edit-reviews` | 按版块、目标类型和状态读取审核队列 |
| GET | `/api/v1/admin/edit-reviews/{review_id}` | 读取审核详情和新旧版本 |
| PATCH | `/api/v1/admin/edit-reviews/{review_id}` | 批准或驳回，携带审核记录 revision |

原主题、回复 PATCH 接口保持入口不变，但返回结果必须明确是 `published` 还是 `pending_review`，前端据此显示“编辑已提交审核”，不能把待审内容当作已发布内容。

## 验收标准

- 主题和回复开关互不影响；至少两个版块可在一次保存中得到不同或相同策略。
- 开启审核后提交编辑，匿名用户和其他用户继续看到旧版本。
- 审核通过后公开内容和修订历史只增加一次；审核驳回后公开内容及修订号不变。
- 插件停用后新的编辑立即发布，既有待审记录仍可由有权限管理员查看和处理。
- 过期基础修订号、过期审核 revision、重复待审提交都返回 409，且不覆盖公开内容。
- OpenAPI、数据库行为、API 契约和前端主要交互都有自动化测试。
