## 1. 产品边界

保留账号与安全、版块/子版块、统一Post/Topic模型、发帖评论、草稿、点赞收藏关注屏蔽、私信通知、搜索、基本治理、简单成长勋章。首页单列非瀑布流；图文与纯文字共用骨架；图片最多9张，feed预览当前用户可访问的前3张；纯文字帖不强塞占位照片。标题可空，正文优先。发布无交易字段、无独立强制预览。版块不是圈子，不展示版块成员数。

EXP、可消费积分、会员用户组、标准权益、勋章、管理角色是独立模型。界面可以合并入口，数据和授权不混并。经验增长不自动等于管理授权；花掉积分不掉成长等级；关闭兑换不撤销既有权益。

可选内置模块包括投票、积分兑换、扩展统计、帖子补充和额外编辑审核；具体启停与历史策略必须在DYR-023冻结。真实第三方Wasm运行时与这些内置模块分开。保留受控命令、幂等和沙箱，不把任意SQL交给扩展。

本轮不增加现金支付/充值提现、插件市场、主题市场、复杂积分公式、活动大屏、微服务或另一套编辑器。新站采用轻量默认；**已有站点升级不得自动关闭已绑定认证、已用存储或已开启业务。**

## 2. 为什么优先做这些

前述静态审阅发现：会员数据集中Promise.all、后台入口统一等SMTP、通知局部未读计数覆盖全局、草稿保存异常被吞却固定提示成功、待办未带对象定位、部分侧栏统计来自当前feed。以上是静态代码发现/推导，尚非运行复现；DYR-001至006需先补测试再修复。来源见`08-sources.md`。

插件运行时已能关闭，后台和前台部分组件已懒加载，S3已有optional feature；不能重复把这些写成全新任务。当前API对plugin-host的构建依赖与业务开关仍需重新划界，见DYR-023至026。

## 3. 信息架构

### 前台

桌面顶栏：品牌 / 搜索 / 发布 / 通知 / 用户菜单。左侧：主页、关注快捷入口、版块、收藏。移动底栏：**首页 / 社区 / 发布 / 通知 / 我的**。关注仍是首页数据维度，不再维护第二份关注状态。个人公开主页与本人控制面板分离；私信在通知区和用户菜单可达，不再增加一个近义底栏。

### 后台

本版采用七组导航，而不是为凑六组把会员与管理权限重新混在一起：

| 一级组 | 二级内容 | 设计约束 |
|---|---|---|
| 工作台 | 我的待办、可验证摘要、快捷入口 | 指向对象，不做装饰大屏 |
| 内容治理 | 主题、评论、举报、编辑审核、风控、审计 | 原流程保留，按任务联动 |
| 版块管理 | 目录、版块设置、有效权限、就地任命 | 支持子版块，不做成员系统 |
| 用户与会员 | 用户、会员用户组、成长、积分、勋章、权益 | 用户组不包含管理职务 |
| 管理团队 | 人员、角色模板、自定义权限、权限检查 | 范围优先，不自动全站授权 |
| 扩展与数据 | 内置扩展、外部插件、数据报表 | 启用状态和权限共同决定入口 |
| 站点设置 | 品牌、邮件、安全接入、存储、运维备份 | 已有配置兼容，按页加载 |

无权限页面不会靠隐藏导航保证安全：服务端独立授权。未启用、无权限、无数据、读取失败四种状态分开。旧15模块的映射见设计规格，不删除原功能。

## 4. 用户组与管理权限

用户组列表显示名称、基础/附加身份、加入方式、有效状态、成员入口和主要能力。默认/自动/人工等来源以实际模型为准，不凭设计图新增。访客是访问场景，不强制创建一个可授予的“游客会员组”。

组编辑页分基本资料、社区权限、使用限额、组内成员、变更记录。权限字段用“本组提供/本组不提供”，不要用“未勾选=禁止”。已有实现对有效来源进行允许合并，额度取MAX；负面限制独立评估。审核要求与正向能力分区，底层映射保留特征测试。

版块矩阵先展示既有规则的有效结果，点击查看来源和计算时刻。组场景不等于任一真实用户；需要权益、账号状态、用量时提示选择具体用户。预设只能生成旧引擎已经支持的规则。父子版块、显式拒绝优先级、覆盖语义不得在UI任务中暗改。

管理团队按“选人员→职务模板→范围→有效期/原因→确认”组织。模板只是已有能力组合。包含子版、期限等选择只有现场契约支持时可启用，不能让前端控件假装实现。高危能力与最后管理员保护需测试。

权限检查只读，不调用会增加daily_quota的消费函数。结果与真实操作共享决策基础，实际请求仍重新判权。只向有权限管理员显示内部来源；普通会员只看到允许公开的拒绝说明。

## 5. 关键用户旅程

| 旅程 | 成功状态 | 失败/边界 |
|---|---|---|
| 首页→版块→发帖→详情 | 当前版块预选，9图有序，幂等成功 | 存储失败/登录失效不丢输入 |
| 通知→某条回复→返回 | 楼层定位、全局未读正确 | 目标受限不泄露摘要，晚到通知保留 |
| 用户组→编辑→比较→保存 | 来源、限额、变更清楚 | 旧revision不覆盖他人修改 |
| 版块→选组访问→任命版主 | 名称选择、范围带入、效果可查 | 不能扩大未授权子版或全站 |
| 工作台→举报→处置→返回 | 直接对象、上下文、逐项结果 | 重复处理/部分失败可解释 |
| 扩展关闭→历史读取→恢复 | 无新动作，历史策略明确 | 不重复奖励、不删除账本 |
| 备份→隔离恢复→核对 | 数据、附件与密钥完整 | 缺项阻断上线，不虚构恢复成功 |

## 6. 数据与接口原则

沿用Rust/Axum、PostgreSQL、React/TypeScript/Vite以及已锁定版本；不顺带升级依赖主版本。复用现有端点。新增unread过滤、权限诊断、效果预览、模块能力摘要只是**候选契约**，必须先检查现有API，再在api-contract定义并生成客户端，不手改生成物。

前端不单独实现权限算法，不把全量私有数据下载再隐藏。数据库写入继续受事务、请求幂等、revision和审计约束。统计必须标明口径、时间、全量/摘要；未知不是0。诊断/预览只读且有授权；真正保存重新判定。

## 7. 实施分层

G0建立基线；G1先修正确性；G2重做管理心智模型；G3完善会员治理；G4统一前台和手机体验；G5裁剪扩展与依赖；G6回归、性能与恢复。每个阶段可形成候选发布，但上一道门禁没过不能用新截图代替功能验收。

公开网址/SEO（DYR-027）是条件任务：公开传播目标确认后执行，不阻塞核心管理体验交付；不承诺搜索引擎收录。没有固定周数与百分比收益承诺，工作量估算由基线和人员明确后单列。

## 8. 成功判据

本轮必须证明：草稿失败不提示已保存；通知计数不依赖当前页；进入举报不等待SMTP；会员按页加载；用户组不手输ID；任命范围可解释；诊断不扣额度；0不等于无限；权限变更后所有入口一致；关闭扩展不破坏历史；基础产物不包含Wasm依赖闭包（完成可选化后）；干净检出、回归与隔离恢复通过。

**内容结构**：搜索、状态、用户组和最近活动筛选；姓名优先。

## 5. 重点流程的实施级约束

用户组编辑：GET载入revision→本地修改→只读差异→提交expected_revision→409保留本机输入并显示远端版本→用户选择重载/重新编辑。复制用户组须明确复制权限和额度，不复制成员、历史授权或管理角色。成功后刷新组摘要和有效权限相关缓存。

权限矩阵：分清“组模板场景”和“具体用户场景”。组模板无法决定该用户的账号限制、附加权益和当日使用量，不应直接宣称任一用户都能完成操作；用“本组提供，仍需具体用户检查”。授予和拒绝来源分别呈现，禁止用同一个开关暗示所有层级全局优先级。

权限检查：选择具体目标与操作，显示 evaluated_at、规则版本、允许/拒绝/无法判断、可见来源、相关限额与用量；数据源错误不默认允许。客户端诊断结果不是访问令牌。导出/复制诊断记录需独立脱敏，不能带会话密钥。

通知：只读本人的数据，filter+cursor+limit服务端一致处理。单条已读提交成功但计数刷新失败时显示同步中/重试，不用当前页数量覆盖全局。全部已读的截止点或事务快照在契约中明确。

发布器：保存状态不是单个布尔值。本机成功但云端失败显示“已保存到本机，云端未同步”；文件仍在内存且未持久化时不能称完整草稿可恢复。未解决上传默认阻止发布并提供移除/重试。最终关闭必须给主动放弃机会，但不会误报安全保存。

## 6. 原型能做什么、不能做什么

原型支持页码导航、名称搜索、权限开关、变更确认、比较跳转、管理人员确认、模拟权限检查、草稿失败与关闭确认、图片顺序变化、全局未读模拟、会员/设置页签、手机菜单。部分次级按钮和筛选仅展示布局或提示，真实API、数据库、上传、鉴权、持久化、批处理与导出均未接入。

所有修改只在当前页面内存中模拟；刷新重置。原型没有实际账户登录，也不接受真实密码、验证码或密钥。它不能用作管理工具部署到生产，也不能用原型UI判断安全性。HTML可以离线打开，不需要安装依赖或启用开发服务。

原型检查仅覆盖本包记录的页面/宽度和模拟交互，不代表真实浏览器兼容、屏幕阅读器验证或原应用E2E完成。完整实施仍按第五章的验收执行。

# 第4部分

# 契约、权限与增量迁移方案

本章定义实施约束和待冻结的候选契约。不存在“照图加字段就算完成”。DYR-002先确认现有代码，DYR-023再冻结模块状态。现有已部署协议与数据优先兼容；安全缺陷不为保持旧行为而继续放行。

## 1. 权限模型与实际执行

对社区写操作，先核对账号状态和有效来源；当前代码中有效用户组允许项与有效标准权益允许项合并。各额度取有效来源MAX，缺省为0。starts_at<=判定时刻且ends_at>判定时刻；到期时刻相等时不再生效。版块访问、内容访问、局部禁言、审核和管理范围在实际调用链上的约束另行追踪，不用一条概括公式替换所有端点。[S11]

界面里“本组不提供”不是显式全局拒绝。一个来源20MiB另一个10MiB，额度是20MiB不是30MiB；0不表示无限。单位转换需安全整数及上下限校验。设置页面单位MiB/GiB与服务端bytes精确换算，避免四舍五入悄悄放宽限制。每日窗口先沿用当前服务端业务日，不能顺带改时区。

治理角色决定哪些管理动作以及可管理范围；会员身份不赋予管理权限。版主也不因此绕过所有内容访问规则。模板只包含现有授权键，操作者须有授权资格，不能通过自定义模板提升自身或他人到不允许的权限。

## 2. 只读诊断与写入的分离

当前authorize_community_action_with_executor在带daily_quota时会使用INSERT/UPSERT消费额度，绝不能把它直接当权限检查接口调用。[S11]

建议抽取可复用的决策数据/规则评估层：只读诊断读取有效来源、目标规则和当前已用额度；操作端继续在真实事务中再次验证并原子消费。共享规则不等于共享副作用。若数据库一致性需要，诊断使用只读事务和明确快照；不持有长时间写锁，不写审计业务表之外的业务状态，诊断审计本身是否记录另按策略确定。

诊断返回是解释性快照，不承诺随后操作一定成功。并发、到期、版块迁移、管理员改规则都会改变结果。实际动作不能直接信任客户端传来的allowed或前次诊断数据。所有故障fail-closed或返回无法判断；不能用上次成功诊断继续放行。

管理员查看他人权限来源要有明确授权、范围限制与查询成本上限。普通成员只看与自己相关且允许公开的原因，不透露隐藏内容标题、其他会员身份或内部风控细节。

## 3. 候选契约清单：先复用，再增量扩展

| 能力 | 最少输入 | 最少结果 | 实施限制 |
|---|---|---|---|
| 用户组搜索 | 名称关键字、分页、状态 | id、显示名、类型、状态、可授权标识 | 复用现有接口；不是全量ID手填 |
| 用户组变更 | id、expected_revision、具体修改、原因 | 新revision、差异摘要、request_id | 保存前重新授权，409保留输入 |
| 有效权限检查 | 用户/场景、目标、动作 | 决定、evaluated_at、可见来源、额度、原因码 | 只读，不消费额度；组场景须标为不完整 |
| 通知列表 | filter、cursor、limit | 条目、next_cursor、必要快照信息 | filter由服务端执行，游标和过滤绑定 |
| 通知已读 | 通知id或明确截止范围 | 状态、服务端计数或可刷新版本 | 幂等；晚到事件语义明确 |
| 模块摘要 | 当前会话/部署 | 可用状态、有效操作能力、原因码 | 不返回密钥或私有安装详情给访客 |
| 管理操作差异 | 当前资源及编辑内容 | 字段差异、受影响范围 | 预览非授权；保存再次校验 |

以上均是逻辑契约名，不预先编造生产URL。先在api-contract追加/复用类型，再生成OpenAPI和TS类型；不得手改src/api/generated产物。错误沿用现有标准封套与request_id。内部详细原因不直接下发公共页面。零差异验证要与此次允许的契约变更清单对比，不把有意新增字段误判失败。

## 4. 通知计数与并发

建议把“全部已读”定义为本次操作取得的服务端快照中已有的本人通知，操作后到达的通知仍保留未读。具体使用事务快照、可靠序列或其他现有机制，由DYR-004冻结，不能只凭客户端时钟或不保证提交顺序的ID猜截止点。

单条已读幂等；请求重试不重复减计数。全局计数不取当前页items.length。快速切换账户、改变筛选、加载更多或页面卸载后，晚到响应不可写回旧页面。游标不能在不同filter下复用。数据库修改与计数读取的一致性及多标签页更新策略必须有用例。

## 5. 四层能力状态

能力有效性分别考虑：①本构建是否支持；②部署运行时是否配置/可运行；③该业务模块是否启用；④当前用户、目标与动作是否获准。内置模块不强制依赖Wasm运行时；外部插件必须满足其运行条件。所有判定以服务端为准，前端只用结果组织页面。

推荐可解释状态：本构建不支持 / 未配置 / 已停用 / 过渡处理中 / 可用 / 运行故障。无权限不是安装故障；无数据不是停用。禁用中的更新、任务和在途请求采用版本/锁或事务一致性机制，具体实现沿用项目能力，不随意引入新中间件。

### 各模块停用的默认建议（须在DYR-023确认）

| 模块 | 停止的新动作 | 历史/在途处理 |
|---|---|---|
| 投票 | 新建、修改、投票 | 仅在原访问权限内按既有结果可见规则展示；停用不能提前公开未结束票数 |
| 兑换 | 新建兑换与新扣分 | 已成交记录、积分流水、已授予权益保留；在途事务按一致边界完成/拒绝 |
| 帖子补充 | 新增/修改补充 | 历史补充在原内容访问边界内可读，不合并改写正文 |
| 编辑审核 | 新规则不再接收或按明确替代路径 | 待审项继续处理或有显式迁移策略，禁止静默自动通过 |
| 扩展统计 | 可选聚合与报表请求 | 保留历史，标最后更新时间；基础治理摘要不被带走 |
| 成长奖励 | 停止新增事件发奖 | 旧账本保留；恢复按水位和幂等去重，不重放出双份奖励 |
| Wasm运行时 | 外部代码执行与其专属任务 | 不等于所有内置模块停用；历史按模块政策读取 |

“卸载”与“停用”不同。首轮默认不实现一键清空数据；需要销毁时另行批准、备份、审计和保留期限。关闭功能不移除所有基础幂等或治理任务。

## 6. 官方扩展迁移：扩展式兼容，不丢历史提供者

阶段一盘点：安装记录、provider_key、权限、配置、版本、队列、任务水位、幂等键、用户授予与所有受影响表。建立旧插件ID到新内置模块的显式映射，不把旧provider字段整体抹掉。

阶段二双读单写：新代码可读取历史与新标识，但同一业务只允许一个写执行器。成长奖励尤其不能内置和Wasm双执行；若复用原幂等键需证明算法一致，不一致则设计映射/已发奖去重边界。

阶段三影子比较：只比较规则结果、不执行副作用。固定时间、事件与用户数据，对比权限/额度/历史查询结果。差异未经批准不切换。

阶段四受控切换：停止旧写入者→确定队列水位/在途事务→启用新唯一写入者→检查账本与任务→监测。失败只回退到仍兼容新数据的版本；不得让旧新写入者并行“保证不丢”。

阶段五清理：兼容窗口与恢复演练通过后再移除替代实现、旧静态面板和不用的依赖。已经停用的老站功能保持停用；没有安装的扩展不在升级中自动启用。

## 7. Rust构建矩阵

API当前plugin-host并非可选，S3已经是infrastructure feature；不能声称现在就能用候选开关构建。[S8][S9]

## 8. 数据迁移和回退

先追加兼容字段/表/索引，再切换读写，最后才考虑删除旧结构。每步提供幂等性、失败恢复和兼容版本说明；索引与数据回填应评估表规模、锁时长和批次，不能因UI任务一把全量重写。

回退分三类：仅UI/配置回退；应用兼容版本回退；数据恢复。回退应用必须说明新写数据是否仍可读写。整库恢复会丢备份时点之后的新写入，应记录RPO并安排写入暂停/补偿，不能宣称“点一下无损回滚”。
